## 1. Engine Qualification & Mandatory Pragma Profile (`F04-A`)

Schegent qualifies Node's built-in `node:sqlite` (`DatabaseSync`, verified at `sqlite_version() = 3.53.4` on Node 24, exceeding the `3.51.3` WAL-reset fix floor). Every operational connection applies and verifies via read-back:

| Pragma | Applied Setting | Required Read-Back | Purpose |
|---|---|---|---|
| `journal_mode` | `WAL` (or `MEMORY` in `:memory:` tests) | `'wal'` / `'memory'` | Concurrent readers alongside a single serialized writer |
| `synchronous` | `FULL` (`2`) | `2` | A committed write survives a process or OS crash; power-loss durability depends on the platform (below) |
| `foreign_keys` | `ON` (`1`) | `1` | Per-connection enforcement of all relational foreign keys |
| `busy_timeout` | `250` | `250` | Bounded `250 ms` lock wait ceiling |
| `trusted_schema` | `OFF` (`0`) | `0` | Hardens against untrusted SQL functions/triggers in schema objects |
| `temp_store` | `MEMORY` (`2`) | `2` | Keeps transient sort/index scratch space in memory |
| `query_only` | `ON` (`1`) on read pool | `1` (readers) / `0` (writer) | Prevents accidental mutations on read connections (`max 2`) |

If any pragma read-back does not match its required value, `NodeSqliteConnection` closes the descriptor and throws `SqlitePragmaVerificationError`.

**Power loss on macOS.** `synchronous = FULL` makes every commit call `fsync`. On Linux that reaches the disk.
On macOS, `fsync` leaves the data in the drive's cache; only `F_FULLFSYNC` flushes it, and SQLite issues that
only under `PRAGMA fullfsync`, which the store does not set. A power cut or a forced shutdown on macOS can
therefore lose the most recent commits. Turning it on was measured and not adopted: on 2026-11-12, 500 one-row
WAL commits under `node:sqlite` on APFS took 63 µs each without it and 4,818 µs each with it. The connection
is synchronous on the extension host thread, so that cost would block the host on every commit.

## 2. Trusted Storage Location, One-Store-Per-Folder Relocation & Network-Share WAL Refusal

`resolveTrustedSqliteLocation` (`src/services/sqlite-store/storage-location-resolver.ts`) enforces:
1. **Trusted Source Origin**: Only `host_storage_uri`, `host_global_storage_uri`, or explicit `cli_state_dir` roots are accepted. Paths supplied by webviews, workspace settings, or untrusted environment variables are refused (`untrusted_source`).
2. **Containment & POSIX Permissions**: Directory chains and the database leaf file are created via `ensureAnchorWithinRoot` and `openWithinRoot` (`src/lib/safe-open.ts`) with `0700` directory mode and `0600` file mode (Hard Rule 69).
3. **Network-Share WAL Refusal**: Opening in `WAL` mode on `nfs`, `smb`, `cifs`, `afp`, `webdav`, `fuse.sshfs`, `smbfs`, or `ncpfs` is refused (`network_share_wal_unsupported`) with an instruction to configure a local `--state-dir`.

**One Store Per Folder (`FR-R7-10`, closing GC-26).** VS Code extension windows resolve their canonical store to `<globalStorageUri>/sqlite/<scope>/schegent-state.db` (`sqliteDatabasePathFor` in `src/activation/sqlite-cutover-wiring.ts`), where `<scope>` is the first 16 hex characters of SHA-256 of the workspace root. This eliminates the split between direct-folder openings and `.code-workspace` openings while leaving explicit CLI `--state-dir` resolution unchanged.

On trusted primary activation (holding `.schegent/ownership`), `relocateLegacySqliteStore` (`src/services/sqlite-store/store-relocation.ts`) executes an idempotent, crash-safe one-time relocation from legacy per-window `storageUri` roots:
- **Host filesystem detection for source and destination (`FR-R7-11`)**: `detectFilesystemType` (`src/services/sqlite-store/filesystem-type-detector.ts`) walks up to the nearest existing ancestor without creating directories and classifies both canonical destination and legacy source mounts as `local`, `network`, or `unknown` (`/sbin/mount` on macOS, `/proc/<pid>/mountinfo` with `/proc/<pid>/mounts` fallback on Linux, UNC/drive classification on Windows). WAL is refused on `network` destinations, and relocating off a confirmed-`local` working legacy store onto an `unknown`/unverified destination is refused with zero writes to the canonical destination; if the legacy source itself is on a `network` filesystem, WAL refusal is reported rather than claiming the legacy store is usable locally.
- **Strict containment & zero-mutation read-only inspection (GC-09, `FR-R7-11`)**: All candidates are verified segment-by-segment via `withZeroMutationReadOnlySqlite` (`src/lib/sqlite-readonly-inspect.ts`), rejecting any symlink along the directory chain (including in-root symlinks), any non-regular `.db` leaf, and any symlink `-wal`/`-shm` sidecar before opening SQLite. When no `-wal` sidecar exists, inspection opens the database via `file://...?immutable=1` (`readOnly: true`) so SQLite creates zero `-wal`/`-shm` files and mutates zero bytes; when `-wal` is present, `.db` and `-wal` are copied into a private `0700` temporary directory (`0600` files) so committed WAL frames are read accurately while the source directory remains untouched and byte-identical. Any candidate recording `min_reader_version` or `schema_version` above the running build is refused untouched and reported.
- **WAL-preserving staging and recovery**. Schegent reserves `.schegent-state.relocate.staging.db` at mode `0600` inside the canonical `<scope>` directory before running read-only `VACUUM INTO`. The snapshot includes committed WAL frames. Schegent syncs the staged file, verifies it with `PRAGMA quick_check`, and records its SHA-256 digest and the source fingerprints in `.relocation-in-progress.json` (`0600`). It checks the ownership fence and publishes the snapshot by atomic rename. On platforms that support syncing directory handles through Node, it syncs the destination directory entries before retiring the legacy files. Recovery checks both schemas and can resume publication from the verified staged image, including after interrupted removal of the previous canonical sidecars. The journal retains the link to the preserved canonical snapshot during recovery. A changed compatible legacy store goes through normal conflict selection. Failed retirement leaves the journal with `retirementPending: true` and warns the operator.
- **Deterministic two-database conflict handling (zero silent merge)**: When two or more populated databases exist for the same `<scope>` (empty zero-row shells are ignored; populated detection covers `operational_*`, `runs`, `definitions`, `artifacts`, `accounting_observations`, `live_log_streams`, and legacy `usage_observations`), the winner is selected deterministically by `(1) highest persisted operational or schema write timestamp` (`Math.max(operationalMaxTs, metadataMaxTs)`, including `accounting_observations.ingested_utc` and `live_log_streams.updated_at_ms`, falling back to max `.db`/`-wal` `mtimeMs` only when both persisted maxima are absent), `(2) highest summed Run count` (`runs + operational_runs`), `(3) canonical store preference`, `(4) lexicographical path order`. Rows are never merged. Unselected legacy databases remain byte-for-byte untouched in place with zero newly created sidecars. Schegent syncs a displaced canonical database snapshot at mode `0400` before publishing it by atomic rename as `schegent-state.unselected-<shortHash>.db` beside the canonical store. Resolved conflict fingerprints are persisted in runtime-validated `relocation-receipt.json` (`0600`), logged via `SanitizedLogger` with zero row content, and surfaced in one operator notice that includes any associated diagnostics.
- **Incomplete discovery & corrupt input diagnostics**: Sibling `workspaceStorage` entries are sorted deterministically before applying the `2,048`-entry scan ceiling. Scan truncation, unreadable parent or sibling directories, malformed receipts, containment refusals, and corrupt canonical or legacy databases are surfaced via bounded path-free diagnostic fields (`corruptCandidateCount`, `incompleteDiscovery`, `retirementPending`, `diagnostics`) with `noticeRequired: true` and sanitized warnings rather than returning a silent `noop`.
- **Unwritable / network-FS fallback**: If the canonical target cannot be prepared (read-only directory, containment refusal, WAL-refused network filesystem, or unverified `unknown` filesystem while a confirmed-`local` legacy store exists), the existing legacy database remains active in place and protected by `getDatabaseProtectedPaths()`, with a warning notice and zero writes to the refused canonical destination or fallback to a third location.

## 3. Live Writer Routing, Bounded Writer Queue, Settlement Reserve & WAL Checkpoint Policy

**Live operational writer routing (`FR-R7-02`, `FR-R7-18` / `N12`).** Post-cutover `WorkspaceStateStore` mutations (`KEYS.queue`, `KEYS.run`, `KEYS.connectedRuns`, `KEYS.terminalTransitionIntent`, history, grants, and acceptance bindings) commit through `SqliteOperationalBacking.updateBatch()` (`src/state/sqlite-operational-backing.ts`) as direct serialized `BEGIN IMMEDIATE ... COMMIT` transactions on `writerConnection` with monotonic `revision = revision + 1` upserts, ordered by `WorkspaceStateStore`'s single promise chain and gated by `.schegent/ownership/` window primacy (Hard Rules 4 and 58). Only `PASSTHROUGH_OWNERSHIP_KEYS` (`KEYS.lock`, `KEYS.executionLeases`, `KEYS.operatorPseudonym`) stay on Memento.

`WriterCoordinator` (`src/services/sqlite-store/writer-coordinator.ts`) enforces the F03/F04 queue and WAL bounds for `AtomicTransactionUnitsService` and qualification workloads:
- **Total Queue Capacity**: `64` requests or `16 MiB` (`16,777,216` bytes).
- **Reserved Settlement Headroom**: `16` slots or `4 MiB` (`4,194,304` bytes) reserved exclusively for the `settlement` lane (`Terminal acceptance`, lock renewal/release, and durability flushes). Normal and background writes are capped at `48` requests or `12 MiB` and rejected with `QUEUE_SATURATED` above that threshold.
- **WAL Checkpoint Escalation**:
  - `PASSIVE`: Triggered at `1,000` accumulated WAL pages or `30,000 ms` since the last checkpoint.
  - `TRUNCATE` / `RESTART`: Triggered when WAL size reaches `64 MiB` and read connections are idle.
  - `WAL_BACKGROUND_PAUSED`: Triggered when WAL size reaches `128 MiB`, pausing `background` priority writes while keeping `settlement` and `standard` lanes operational.

Multi-table relational CAS/lease-fenced transaction units (`expectedRevision` Compare-And-Set, `lease_fences`, `steps`, `attempts`, `operation_receipts`, and `state_change_outbox`) execute inside `AtomicTransactionUnitsService` (`src/services/sqlite-store/transaction-units.ts`) — distinct from `SqliteOperationalBacking.updateBatch()` above (which commits live `WorkspaceStateStore` schema-9 per-entity rows, relational `runs`/`containment_acceptance_bindings`, and `operational_kv_documents`):

## 5. Seven-Stage Migration Pipeline, Quarantine & Online Backup/Restore

1. **Migration Stages (`MigrationCoordinator`)**:
   - `prepare-copy → import → quiesce/reconcile → validate → publish-authority → retain-source → retire-source`.
   - Any interruption prior to `publish-authority` leaves `cutover_sentinel.authority = 'legacy'` and resumes idempotently on restart.
   - Corrupt JSON or unknown-future-version (`schemaVersion > maxSupported`) records are preserved in `migration_quarantine` with full raw payload and diagnostic JSON (`0` silent drops). `retire-source` is blocked until all quarantine rows are resolved.
   - Once `publish-authority` completes, `CutoverAuthorityGuard.checkLegacyAccessAllowed` refuses legacy Memento/JSON access (`SQLITE_AUTHORITY_ACTIVE`).
2. **Online Backup, Verification & Full-Authority Restore (`BackupRestoreService` & Operator Commands, `FR-R7-03`, `FR-R7-14`)**:
   - `createOnlineBackup` uses `VACUUM INTO` to snapshot the live WAL database into `<globalStorageUri>/sqlite/<scopeId>/backups/` (with legacy per-window `storageUri` used only when the canonical target is unwritable or WAL-refused; `0700` dir, `0600` `.db` and companion `.db.manifest.json` via `ensureAnchorWithinRoot`/`openWithinRoot`/`narrowMode`). Both the live SQLite store and backups reside outside the workspace and survive workspace directory deletion.
   - `createOnlineBackup` enforces the same dependency ceilings upfront as verification (`10,000` external dependencies, `512 MiB` external dependency bytes, `16 MiB` manifest, `512 MiB` database image), refuses over-limit creation with an actionable error (`EXTERNAL_DEPENDENCY_BOUND_EXCEEDED` / `BACKUP_MANIFEST_BOUND_EXCEEDED`), and unlinks all partial `.db`, `.tmp`, `.manifest.json`, and sidecar artifacts on failure so no unusable backup is published.
   - **Deletion-history preservation (`FR-R7-14` / `14-01`)**: external artifact dependency collection joins `artifact_lifecycle` and `artifact_availability` so rows whose bytes were intentionally deleted through the artifact lifecycle (`deleted`, `expired`, or fallback `evicted`) retain their SQLite tombstones across backup, verify, and restore without requiring deleted bytes on disk, while any genuinely missing or corrupt *live* external dependency still causes pre-write refusal (`EXTERNAL_DEPENDENCY_MISSING_OR_CORRUPT`).
   - `verifyBackup` and `validateAndRestoreBackup` reject SQLite sidecars (`-wal`, `-shm`, `-journal`) and recompute the file-byte SHA-256 digest before opening SQLite. They check that the manifest accounts for required live external dependencies and enforce the `10,000`-entry / `512 MiB` ceilings. In a read-only connection they check SQLite and foreign-key integrity, `schema_version`, `min_reader_version`, and the applied migration checksums.
   - `validateAndRestoreBackup` replaces all `128` tables in `AUTHORITATIVE_RESTORE_TABLES` (`src/services/sqlite-store/authoritative-restore-tables.ts`, gated against all `CREATE TABLE` definitions and `sqlite_master` by `tests/lint/sqlite-authoritative-restore-census.test.ts`) atomically inside a single `BEGIN IMMEDIATE ... COMMIT` transaction with `PRAGMA defer_foreign_keys = ON`, transactional trigger preservation, pre-restore / post-validation / pre-`COMMIT` ownership primacy & idle re-verification (`RESTORE_OWNERSHIP_LOST`, `RESTORE_BUSY`), and pre-commit `PRAGMA foreign_key_check`, followed by operational cache reload (`reloadCacheFromSqlite`), handoff target-lookup reload, and UI snapshot refresh (reporting `committed_refresh_failed` distinctly if post-commit refresh throws).
   - Exposed to operators via **Schegent: Back Up Store** (`schegent.backupStore`, mutating, owner-only), **Schegent: Verify Store Backup** (`schegent.verifyStoreBackup`, read-only), and **Schegent: Restore Store Backup** (`schegent.restoreStoreBackup`, mutating, owner-only, refused with `RUN_IN_FLIGHT` while any Run is non-terminal), backed by the zero-`vscode` headless API in `src/headless/backup-restore-api.ts`. Backup and restore append sanitized metadata-only `store-backup` / `store-restore` audit rows (zero raw paths).
   - For rolling back a failed migration or bad upgrade across a `min_reader_version` bump (schema `N` → `N-1`), see [`sqlite-rollback-runbook.md`](sqlite-rollback-runbook.md).

## 6. Per-Entity Operational Rows and Migration 9 (`FR-R7-02`)

Baseline host-thread measurement on schema 8 (`WAL` + `synchronous = FULL`) exceeded the Round 6 event-loop budget (`worst write commit p95 = 21.490 ms > 20 ms`), triggering forward-only checksummed Migration 9 (`009_fr_r7_02_operational_per_entity_rows`; see [`sqlite-operational-commit-latency-measurement.md`](sqlite-operational-commit-latency-measurement.md)):

- **Schema & reader floor**: `SQLITE_SCHEMA_CURRENT_VERSION = 9`, `SQLITE_MIN_READER_VERSION = 9`. Older builds (`maxSupportedVersion <= 8`) fail closed at open with `UNSUPPORTED_MIN_READER_VERSION` without modifying the database file.
- **Per-entity `STRICT` tables**:
  - `operational_queue_meta (scope_id, queue_id, ...)` — queue lifecycle metadata plus lossless `remainder_json`.
  - `operational_tasks (scope_id, queue_id, task_id, ...)` — indexed by `(scope_id, queue_id, position ASC)` with lossless `payload_json`.
  - `operational_runs (scope_id, queue_id, run_id, ...)` — indexed by `(scope_id, run_id)` with lossless `payload_json`.
- **Atomic transactional backfill**: Migration 9 copies existing `schegent.queue` and `schegent.run` maps from `operational_kv_documents` inside the single migration transaction, verifies exact row counts and canonical SHA-256 content digests against the source documents, and rolls back completely on any error or mismatch. Bare legacy queue and Run documents remain available to the workspace-state migrators. Malformed maps refuse the SQLite upgrade and leave the source intact.
- **Incremental writes & frozen views**: `SqliteOperationalBacking.updateBatch` diffs incoming queue/Task, Run, and relational `runs` projections inside one `BEGIN IMMEDIATE ... COMMIT` transaction, writing only changed entity rows and incrementing only their revisions. `get()` returns deeply frozen, structurally-shared snapshot views in O(1) without per-read whole-document `structuredClone`, reducing single-Task `p99` latency at `documented-max-capacity` (2,000 Tasks) from `4.054 ms` to `0.231 ms` and overall worst write-commit `p95` from `21.490 ms` to `2.380 ms` (single-platform `darwin/arm64` measurement).

## 7. F04 Placeholder Usage & Log Table Ownership (`FR-R7-16` / `16-08`)

Migration 1 (`001_f04_application_store`) created seven domain placeholder tables before F06 (Migration 3, `accounting_*`) and F07 (Migration 4, `live_log_*`) introduced their dedicated schemas. Under SQLite schema version `9` (`SQLITE_SCHEMA_CURRENT_VERSION = 9`, `SQLITE_MIN_READER_VERSION = 9`), Schegent **retains all seven F04 tables as deprecated, empty-in-production placeholders** rather than dropping them in a schema-10 migration so Migration 1 checksum immutability and schema-8/9 backup/restore compatibility remain unbroken:

| F04 Placeholder Table | Active Authoritative Replacement | Readers / Writers / Relocation / Restore Inventory |
|---|---|---|
| `usage_observations`, `usage_corrections`, `usage_accounting_applications`, `attempt_usage_revisions` | **F06** (`accounting_*`, 11 `STRICT` tables via `createUsageAccountingService`) | Deprecated F04 adapters (`UsageStoreAdapter`, `AtomicTransactionUnitsService.executeUsageCorrection`) are never called in production (unit tests only). `STRUCTURED_STATE_CENSUS` maps `usage-and-cost-ledger` to `accounting_*`. `store-relocation.ts` inspects `accounting_observations` (`ingested_utc`) alongside legacy `usage_observations`. `AUTHORITATIVE_RESTORE_TABLES` preserves both active `accounting_*` and empty F04 tables across backup/restore. |
| `log_streams`, `log_segments`, `log_gaps` | **F07** (`live_log_streams`, `live_log_segments`, `live_log_coverage` via `LiveLogIndex`) | Deprecated F04 adapter (`LogIndexStoreAdapter`) is never called in production (unit tests only). `STRUCTURED_STATE_CENSUS` maps `log-segment-index` to `live_log_*` and `log-segment-bytes` to `live_log_segments`. `store-relocation.ts` inspects `live_log_streams` (`updated_at_ms`). `backup-dependency-collector.ts` queries `log_segments` cleanly (zero rows in production), and `AUTHORITATIVE_RESTORE_TABLES` preserves both active `live_log_*` and empty F04 tables across backup/restore. |

- **Production guarantee**: Production activation (`src/activation/sqlite-cutover-wiring.ts`) writes zero rows to the seven F04 placeholder tables.
- **Retirement trigger**: Dropping the seven placeholder tables and removing `UsageStoreAdapter`, `LogIndexStoreAdapter`, and `executeUsageCorrection` is deferred until a future breaking `min_reader_version` migration that also introduces retired-table restore handling in `BackupRestoreService`, `AUTHORITATIVE_RESTORE_TABLES`, and `backup-dependency-collector.ts`.
